# F4 — Essenciais de suporte: plano

> **Objetivo da fase:** um técnico consegue fazer um **atendimento real de ponta a ponta**: entrar no
> computador (inclusive na tela de login e nos prompts de UAC), reiniciá-lo e voltar sozinho, trocar
> texto e arquivos com o cliente e conversar com ele, sempre com o consentimento de quem está do outro
> lado.
>
> Base: seções [3](../ARCHITECTURE.md#3-o-aplicativo), [4.5](../ARCHITECTURE.md#45-multi-monitor),
> [5](../ARCHITECTURE.md#5-input-e-demais-canais) e [7](../ARCHITECTURE.md#7-identidade-contas-e-segurança)
> do ARCHITECTURE.

---

## 1. Ponto de partida

| Peça | Estado hoje (fim da F3) | O que muda na F4 |
|---|---|---|
| Processo no host | Um app de linha de comando (`HextRemote host`) aberto pelo usuário | **Instalado:** serviço do sistema (`hext-service`) mais um *agent* por sessão. O modo portátil continua |
| Telas que o host alcança | Só a área de trabalho do usuário que abriu o app | Tela de login, UAC e `Ctrl+Alt+Del` no Windows |
| Autorização | Pedido de aceite no terminal do host, a cada conexão | Aceite numa janela, com permissões; **senha não assistida (PAKE)** quando o dono ligar |
| Identidade | Uma chave por usuário (`%APPDATA%`) | Instalado: uma chave **da máquina** (`%ProgramData%`, DPAPI da máquina), com o ID da máquina |
| Canais da sessão | Vídeo, mouse e teclado | Clipboard, arquivos, chat, troca de monitor, reiniciar |
| Interface | Terminal; a janela do visualizador mostra só o vídeo | Interface gráfica mínima no host e no técnico (decisão 1) |

## 2. As peças

### 2.1 Serviço e agent no Windows

Segue a seção 3.4 do ARCHITECTURE:

```
hext-service (SYSTEM, sessão 0)
   ├─ sinalização, presença e conexões (iroh): a sessão sobrevive à troca de usuário e ao logoff
   └─ lança ──► hext-agent (SYSTEM, na sessão do console ativo)
                   ├─ captura + encode, injeção de input, clipboard
                   └─ segue o desktop de entrada: Default ↔ Winlogon (login, UAC, Ctrl+Alt+Del)
```

- O serviço é dono da rede. O agent conversa com ele por um **named pipe** com ACL (só SYSTEM) e manda
  os quadros já codificados. Assim, a conexão com o técnico não cai quando o agent é relançado (logoff,
  troca de usuário, troca de sessão RDP).
- **Lançar o agent:** `WTSGetActiveConsoleSessionId`, depois o token do próprio serviço duplicado com
  `TokenSessionId` trocado e `CreateProcessAsUser` em `winsta0\default`. O agent roda como SYSTEM, o
  único jeito de ver o desktop Winlogon.
- **Troca de desktop:** o agent acompanha `OpenInputDesktop`. Quando ele muda (login, UAC), o agent
  chama `SetThreadDesktop` e recria a duplicação DXGI, que devolve `ACCESS_LOST` nessa hora. O
  `SendInput` passa a valer no desktop novo.
- **`Ctrl+Alt+Del`:** `SendSAS` a partir do serviço. Exige a política `SoftwareSASGeneration`, que o
  instalador liga.
- **Instalação:** `HextRemote service install|uninstall|status`, com serviço automático e reinício em
  caso de falha. O instalador `.msi` fica para a F6.

### 2.2 Identidade da máquina

- No modo instalado, o ID é **da máquina**, não do usuário. A chave fica em
  `%ProgramData%\HextRemote\device.key`, com ACL só para SYSTEM e administradores, e cifrada pelo DPAPI da
  máquina (`CRYPTPROTECT_LOCAL_MACHINE`).
- O modo portátil continua com a chave do usuário (`%APPDATA%`), cifrada pelo DPAPI do usuário.
- Se a mesma máquina rodar os dois, são dois IDs. O app portátil avisa quando o serviço está instalado.

### 2.3 Aceite e permissões

- O pedido de aceite vira uma **janela** no host, mostrada pela interface na sessão do usuário (decisão
  5): nome e ID do técnico, **Aceitar/Recusar** e as permissões da seção 7.2 (ver, controlar, clipboard,
  arquivos e reiniciar). Arquivos vem desmarcado.
- As permissões viajam para o técnico e valem no host: o que não foi concedido é recusado pelo host,
  não só escondido no técnico.
- **Indicador de sessão ativa** (seção 7.3): uma barra sempre visível no host enquanto há alguém
  conectado, com o nome do técnico e um botão **Encerrar**. É obrigatória, inclusive no acesso não
  assistido (seção 7.4).
- **Onde a interface não aparece:** na tela de login e com o computador bloqueado não há janela do
  usuário. Ali o pedido continua numa caixa de mensagem do sistema (só "ver e controlar"), e a barra
  volta quando o usuário entra. Com o computador bloqueado, o técnico é avisado de que alguém precisa
  acordar a tela para ver o pedido. Durante a sessão, o agent (SYSTEM) mostra nessas telas um indicador
  próprio, uma janela Win32 com o nome do técnico e **Encerrar**.

### 2.4 Senha não assistida (PAKE)

- O dono liga o **acesso não assistido** e define uma senha. Isso exige administrador, porque vale para a
  máquina.
- Com a senha, o técnico entra sem que ninguém aceite. A senha nunca trafega: os dois lados rodam
  **SPAKE2** (crate `spake2`) sobre a conexão já aberta pelo `iroh`. A transcrição é amarrada às chaves
  públicas dos dois, então um relay ou o servidor no meio não conseguem nem descobrir a senha nem se
  passar por um lado.
- O host guarda só o derivado da senha (Argon2id com sal), dentro do arquivo protegido da máquina.
- **Contra força bruta:** além do bloqueio do ID no servidor (F3), o host conta as falhas: depois de 5
  falhas, espera crescente (1 min, 5 min, 15 min...) por técnico e no total.
- Continua havendo **indicador visível** e **auditoria** (no host e no servidor).
- **Como entra:** o técnico pede pelo ID marcando que vem com senha; o serviço não pergunta a ninguém e
  emite um código de uso único que só abre a sessão junto com a senha. Assim, cada tentativa passa pelos
  limites do servidor. Até entrar, quem usa a senha fica no limite de estranhos (3 pedidos em 10 minutos
  por aparelho, e o host fecha para estranhos por 15 minutos depois de 10 pedidos no total). O servidor
  não vê a senha: quem diz se o técnico entrou é o host (seção 2.5).
- **Ordem de atualização:** primeiro o servidor. Um servidor antigo não conhece a mensagem `Waiting` e
  derruba a conexão do host novo a cada pedido com a tela bloqueada.
- **Onde vale:** só no serviço instalado. `service password` liga e troca a senha, `--off` desliga, e
  `service uninstall` apaga a senha. O registro fica em `audit.log`, na pasta da máquina.
- **Técnico:** a senha vai ao visualizador pela entrada padrão, nunca como argumento, e não é guardada.
  A tela inicial guarda só o nome e o ID dos computadores acessados (`computers.json`); o catálogo
  sincronizado por conta continua na F5.

### 2.5 Reiniciar e reconectar

Segue a seção 3.3 do ARCHITECTURE: quando o técnico pede para reiniciar (com a permissão "reiniciar"), o
host guarda um **token de reconexão**:
- de uso único;
- válido por 10 minutos;
- amarrado à chave do técnico.

O técnico vê *"Aguardando a máquina voltar…"*. No boot, o serviço volta online, e o técnico reconecta
apresentando o token, sem novo aceite. Ainda há indicador e auditoria. Exige o modo instalado.

Quedas de rede no meio da sessão também reconectam sozinhas, sem perder o estado.

Como ficou (marco 5):
- O técnico aperta **Ctrl+Alt+R** duas vezes em até 5 segundos. A primeira só avisa no título da janela.
- A permissão "reiniciar" vem da janela de aceite, desmarcada, ou da senha não assistida. Quem aceita pela
  caixa de mensagem (tela de login ou bloqueio) não concede essa permissão. O app portátil não reinicia.
- Toda sessão pelo ID recebe um token novo. O host guarda só o hash, e o técnico volta sem aceite e sem
  senha: até 2 minutos depois de uma queda de rede e até 10 minutos depois de reiniciar.
- Antes de reiniciar, o serviço grava o hash em `resume.json`, na pasta da máquina, e o arquivo vale para
  um boot. O reinício leva 5 segundos e fecha os programas abertos, sem pedir para salvar.
- O pedido de volta usa `Connect.unattended`. Se o host ainda acredita na sessão perdida, ele a encerra
  antes de responder.
- Encerrar pelo host, ou fechar o visualizador, apaga o token, inclusive durante a contagem do reinício.
  Sessões pelo IP não reconectam.
- **Quem entrou pela senha não esgota o limite de estranhos ao voltar.** Depois de cada tentativa com a
  senha, o host conta ao servidor como ela terminou (`Attempt`): entrou, com a senha ou com o token, ou
  errou a senha.
  - Quem entrou fica de fora dos limites de 3 pedidos e de 10 pedidos por host, e do fechamento do host,
    por 7 dias desde a última entrada. Vale só para pedidos com senha, que não incomodam ninguém: pedir
    aceite continua no limite. Esperar o host ficar online nunca contou nesses limites, e os limites por
    aparelho e por IP continuam valendo (10 e 30 pedidos por minuto).
  - **Quem nunca entrou fica como antes.** Senha errada não dá nada, e um técnico continua com 3 pedidos
    em 10 minutos.
  - **A primeira senha errada acaba com a confiança.** Se a senha mudou, ou se levaram a chave de um
    técnico antigo, ele tem um palpite antes de voltar ao limite de estranhos. O palpite não escapa do
    relato: na SPAKE2, o técnico só sabe se acertou depois de mandar a prova, e aí o host já decidiu. O
    bloqueio por falhas no host (seção 2.4) continua igual. Isso vale para a confiança ganha pela senha:
    quem uma pessoa aceitou nos últimos 90 dias continua passando, com os limites por aparelho e o bloqueio
    no host.
  - **Ninguém se declara confiável.** O host só fala por si, e o servidor só aceita "entrou" de um host
    que deixou passar um pedido com senha desse técnico nos últimos 5 minutos. O técnico não tem como
    mandar essa mensagem em nome do host, e a mensagem de outro aparelho só vale para aquele aparelho.
  - **Sem ordem de atualização:** o servidor novo avisa no `welcome` (`takes_attempts`) que aceita
    `Attempt`, e o host só manda se ouvir isso. Com o servidor antigo ou com o host antigo, tudo fica como
    antes. Se o host estiver sem servidor, o relato espera a próxima conexão. Um relato pego pela queda da
    conexão se perde: sem "entrou", a volta conta como estranho; sem "errou", vale o da próxima senha errada.
- Reiniciar em Modo Seguro fica para depois.

### 2.6 Canais da sessão

| Canal | Primeira versão | Depois |
|---|---|---|
| **Clipboard** | Texto, nos dois sentidos, quando muda (Windows: contador de mudanças do sistema; macOS e Linux: compara o texto). Liga e desliga por sessão | Imagens; arquivos copiados |
| **Arquivos** | Arrastar e soltar na janela do visualizador envia para a pasta Downloads do host; o host pode mandar arquivos para o técnico, que confirma cada um. Um stream QUIC por arquivo, com tamanho e hash, em ritmo que cede à latência para não atrapalhar o vídeo | Gerenciador de dois painéis; retomar transferências |
| **Chat** | Texto, numa janela pequena nos dois lados | Histórico na auditoria |
| **Multi-monitor** | Lista de monitores no início da sessão; troca com `Ctrl+Alt+1..9` ou pelos botões numerados numa barra recolhível na janela do técnico (keyframe na troca) | Miniaturas, todos lado a lado, uma janela por monitor (seção 4.5) |

A barra de sessão abre completa, com quem está conectado e o que pode fazer, e recolhe 6 segundos depois.
Recolhida, ela vira uma faixa fina e translúcida na borda de cima da tela, com o ponto vermelho, visível para o
usuário e para o técnico. A faixa não tem **Encerrar**, então um clique sem querer não derruba a sessão. Passar
o mouse abre de novo, e uma mudança na sessão também. No Mac, a faixa é opaca.

Como ficou o clipboard (marco 6):
- A permissão vem da janela de aceite, desmarcada, ou da senha não assistida. Quem aceita pela caixa de
  mensagem não concede essa permissão. O host recusa o texto sem ela, mesmo de um cliente modificado.
- Só passa o que muda durante a sessão. O que já estava copiado antes de conectar fica fora.
- No host instalado, quem lê e grava o clipboard é o agent, na sessão do usuário. A sessão continua se o
  clipboard não abrir.
- O limite é de 512 KB de texto. Um texto maior não é enviado.
- No Windows, o que gerenciadores de senha marcam para não monitorar (`ExcludeClipboardContentFromMonitorProcessing`)
  não sai do computador.
- O conteúdo do clipboard não vai para logs nem para a auditoria.

Como ficou o chat (marco 8):
- No host, o botão **Chat** da barra de sessão abre uma janela pequena. A barra não cresceu: o nome do técnico
  encurta para dar lugar ao botão. Na janela do técnico, é o botão com um balão, ao lado dos outros, ou
  `Ctrl+Alt+C`.
- Uma mensagem abre a janela do outro lado sem tirar o foco de quem está digitando. Enter envia, e Shift+Enter
  muda de linha.
- A janela é da interface. No técnico, o visualizador troca mensagens com a interface que o abriu, pela entrada
  e saída padrão. Um `hext view` aberto pelo terminal não tem chat, e `Ctrl+Alt+C` vai para o host.
- O texto do outro lado é só texto: entra na página por `textContent`, sem link, e chega limpo de caracteres de
  controle e de marcas que invertem a leitura. Cada mensagem tem até 8 KiB, cada lado aceita 10 por segundo, e a janela guarda as últimas 200.
- As mensagens ficam na memória da interface, não vão para o disco, e `Debug` não mostra o conteúdo, então elas
  não chegam aos logs.
- O chat não depende de permissão: quem só vê também conversa.
- Sem interface no host (tela de login, por exemplo), o técnico lê "Ninguém recebeu". Com a tela bloqueada e a
  interface aberta, a mensagem chega à janela, mas só aparece depois do desbloqueio.
- Se o mesmo ID voltar, a conversa continua. Se for outro, ou uma conexão sem ID, ela fecha antes: ninguém lê o que o anterior
  escreveu.

Como ficou o multi-monitor (marco 8):
- O monitor principal é o 1, e os outros seguem da esquerda para a direita. Vale para `Ctrl+Alt+1..9`, para
  os botões e para `--display`, que conta a partir de 0.
- Os botões numerados ficam no topo da janela do técnico, à esquerda do botão de tela cheia, e sobem junto com
  ele quando o mouse encosta na borda de cima. Com mais de um monitor, eles aparecem sozinhos por 4 segundos no
  início da sessão. O título mostra "monitor 2 de 3". Com um monitor só, nada muda.
- A permissão de ver cobre todos os monitores: quem só vê também troca, e o mouse continua sem chegar ao host.
- A troca reabre a captura no host e pede um keyframe. O encoder continua e se ajusta ao novo tamanho. Os
  encoders aquecidos da seção 4.5 ficam para depois, com as miniaturas.
- O mouse vai para o monitor mostrado, em pixels físicos no Windows e em pontos no macOS. Cada quadro diz de
  qual monitor é. Enquanto a imagem nova não chega, o técnico não move nem clica (até 2 segundos), para não
  acertar o outro monitor sem ver. Soltar um botão sempre passa. Quando ela chega, o cursor do host vai para
  onde o mouse do técnico está, e o próximo clique cai no monitor que ele vê.
- O host confere os monitores a cada 3 segundos. Se o monitor mostrado sair, a sessão volta ao principal; se ele
  mudar de lugar na área de trabalho, o mouse acompanha. Se a troca falhar, a imagem continua onde estava, e o
  mouse volta depois dos mesmos 2 segundos.
- No host instalado, a troca passa pelo agent, e o agent que substituir o anterior continua no mesmo monitor.
  Depois de uma queda de rede ou de reiniciar, o técnico pede de volta o monitor em que estava.

### 2.7 macOS

- **Inicialização automática:** um LaunchAgent do usuário (sessão Aqua) via `SMAppService`. Isso pede o
  app empacotado (`.app`); até a F6, um `.plist` instalado pelo comando `service install`.
- **Tela de login:** um LaunchDaemon mais um agent no contexto `LoginWindow`. A Apple restringe isso, e
  exige o app assinado. Na F4: **reconectar depois do login** (decisão 3).

Como ficou (marco 9):
- `HextRemote service install`, **sem sudo**, monta `~/Library/Application Support/HextRemote/HextRemote.app`
  (pacote com o identificador `br.com.hext.remote`, assinado ali mesmo, ad hoc) e instala um LaunchAgent do usuário (`~/Library/LaunchAgents/br.com.hext.remote.plist`, sessão Aqua). A cada
  login, ele abre o app sem janela e sem ícone no Dock. Rodar de novo atualiza.
- O ID é o mesmo do app aberto à mão: a chave continua a do usuário. Com o app instalado, abrir o app mostra a
  janela daquele que já está rodando, e fechar as janelas não o tira do ar. Se o app aberto à mão já estiver
  rodando na instalação, ele fica no lugar do instalado até o próximo login.
- As permissões de Gravação de Tela e Acessibilidade passam a ser do **Hext Remote** (o pacote), não do
  Terminal. Com um programa solto, sem pacote, o macOS não reconhecia a permissão dada nos Ajustes. Faltando
  alguma, o app abre a janela com o aviso. Cada versão nova pede de novo, porque o binário ainda não é assinado.
- **Reiniciar** (com a permissão, `Ctrl+Alt+R` duas vezes): o hash do token vai para `resume.json` na pasta do
  usuário (só ele lê), e o Mac reinicia como pelo menu Apple. Os apps recebem o pedido para fechar, e um app com
  algo sem salvar pode segurar o reinício. Na primeira vez, o macOS pode pedir para o HextRemote controlar o
  loginwindow, e o técnico pode clicar no pedido. Depois do boot, o técnico volta sozinho quando alguém entrar,
  se for em até 10 minutos. Quedas de rede também reconectam.
- **Sem senha não assistida no Mac:** sem nada rodando como root, a senha ficaria ao alcance de qualquer
  programa do usuário. Ela entra junto com o LaunchDaemon e a tela de login (F6). `service password` explica
  isso.
- `service status` mostra se está rodando e o ID. `service uninstall` tira do login e apaga o programa
  copiado, e `--purge` apaga também a chave: o ID muda também para o app aberto à mão. A auditoria do reinício
  fica em `audit.log`, na pasta do usuário.

Como ficou o nome do computador (marco 10):
- `service install --name "Recepção"` dá o nome na instalação, e `service name "Recepção"` muda depois.
  `service name` sozinho mostra o nome, e `--reset` volta ao nome do sistema (o hostname), que é o padrão.
- O nome vai para o técnico no começo da sessão. Ele aparece no título da janela, no chat e na lista de
  computadores da tela inicial, que se atualiza na próxima conexão. Do lado do técnico, o nome dele é o que o
  host vê na janela de aceite.
- O nome fica em `name.txt`. Com o serviço do Windows, fica na pasta da máquina, e só um administrador muda. O
  serviço reinicia para usar o nome novo, então uma sessão em andamento cai. Sem o serviço, e no Mac, fica na
  pasta do usuário. No Mac instalado, o app reabre sozinho. No app aberto à mão, vale na próxima abertura.
- Até 64 caracteres, mostrados só como texto: caracteres de controle e marcas que invertem a leitura saem,
  também de um `name.txt` editado à mão.

## 4. Testes

- **Unitários:**
  - SPAKE2 com senha certa e errada;
  - amarração da transcrição às chaves (outra chave falha);
  - token de reconexão (uso único, validade, chave do técnico);
  - contagem de falhas;
  - formato das mensagens dos canais novos.
- **Integração (CI):** sessão em processo com clipboard, arquivo (hash), chat, permissão negada, senha
  não assistida e reconexão com token.
- **Windows no CI:** instalar e remover o serviço num runner Windows (sem tela de login).
- **Campo:** a tela de login e o UAC só dá para testar numa máquina real (ou VM). Roteiro manual no PR de
  cada marco.

## 5. Segurança (o que a F4 precisa garantir)

- O agent roda como SYSTEM: ele só aceita ordens do serviço (pipe com ACL só para SYSTEM) e não abre
  nada para a rede.
- **Nada sem consentimento:**
  - o acesso não assistido é ligado pelo dono, com administrador;
  - o indicador de sessão é obrigatório e não há modo oculto (seção 7.4).
- **Permissões valem no host:** um técnico sem "arquivos" não consegue mandar arquivos, mesmo com um
  cliente modificado.
- **Arquivos recebidos:**
  - vão para Downloads, nunca são executados;
  - nomes com `..` ou caminhos absolutos são recusados;
  - o tamanho e o hash são conferidos antes de o arquivo ganhar o nome final, e nada é substituído;
  - no serviço, tudo roda com os direitos do usuário logado, nunca como SYSTEM;
  - no técnico, cada arquivo vindo do host pede confirmação: quem dá a permissão é o host.
- **Senha:** nunca trafega, nunca é guardada em claro, e as falhas são limitadas.
- **Token de reconexão:** uso único, curto e amarrado à chave do técnico. Ele não vale para outro técnico.

## 6. Decisões (29/10/2026)

1. **Interface:** Tauri 2 agora. A casca da UI (ID, aceite com permissões, indicador de sessão, chat e

   para quando o app for assinado (F6).

5. **A interface roda como o usuário, nunca como SYSTEM** (marco 3, muda a seção 2.3): um WebView na
   sessão do usuário com os direitos do sistema seria um caminho de escalada de privilégio. O serviço
   lança `HextRemote ui --pipe <nome>` com o token do usuário logado, por um pipe aberto só ao SYSTEM e a
   esse usuário, e confere o processo do outro lado. A interface só responde pedidos e encerra sessões.
   No modo portátil, o host roda no próprio processo da interface, com as mesmas mensagens. As duas
   dividem a mesma instância: com o app portátil aberto, a interface do serviço espera ele fechar, e o
   serviço pergunta pela caixa de mensagem até lá.
